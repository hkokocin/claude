# User Review

Two cases: your own change, where you start the app yourself, or a Friend's change (/atui, Friends), where the Friend started the app and sent you its Message.

1. Set the Task's status to `review` (/atui); for a Friend's change, its Subtask (`task="<project>/<number>"`).
2. **Own change**: start the app locally on a free port. As an atui Agent, start it in a new window `app` of your tmux session (`tmux new-window -d -t "=$(tmux display-message -p '#S'):" -n app '<command>'`), so the user sees its logs.
   * backend: against the **dev** database; frontend: against the **dev** services
   * a branch that brings migrations never touches dev: it runs through `atui resources run -- <command>` on databases of its own (/agent_database), seeded with some data

   A Friend starts its app the same way, in its own session, before it sends its Message.
3. Tell the user: the pull request, the URL, the curl file for backend work, what to try, what /review left open, and which database it runs on. For a Friend's change, relay its Message.
   As an atui Agent, the merge is asked as a Decision on the Stream of the Task whose pull request it is, for a Friend's change on its Subtask (`task="<project>/<number>"`), so the waiting approval shows as an action for the user. aservice posts it itself, the approval request, when the pull request becomes ready for review (/atui, Approval requests): look for it among `threads(source="github", state="open")` (for a Friend's change with `task="<project>/<number>"`), the Decision titled "Merge <PR title>?" (the others are event Threads), and tell the user it is on the Stream. Only while there is none (aservice gets no events until the Relay is connected; then this fallback goes), post it yourself: `post(body, title="Merge <PR title>?", question=True, options=[{"title": "Merge", "detail": …, "recommended": True}, {"title": "Request changes", "detail": …}])`, its body what you tell the user in the session, with the pull request and the app as links. When the user already said in the session that you merge a Friend's pull requests on your own, post none for them.
   **Every question on the Stream**: each point the user must decide before the merge, each point /review left open that needs a choice and each change you recommend before the merge, is its own Decision with options, the recommendation marked, on the same Stream as the merge Decision (the Subtask's for a Friend's change), posted before you ask it in the session. Points that need no choice stay in the merge Decision's body. Any other question you ask the user in the session is posted first as a Question (/atui, Stream). The merge Decision's body names those Decisions ("Decide threads <id>, … first"); on aservice's approval request, whose body and options are fixed, reply on it with that reference instead.
   **One recommendation**: what the Stream recommends agrees with what you recommend in the session. When you recommend a change before the merge, your own merge Decision recommends "Request changes", not "Merge"; on aservice's approval request, say so in that Reply.
4. Wait for the user's approval: the newest Choice on the merge Decision is "Merge", or they approve in the session, which you record on the Decision with `choose(thread, [0])` before you merge. Changes they ask for (the Choice "Request changes", then their Replies on that Thread, or their words in the session) are recorded on the Stream (/atui, Stream) and go through /implementation and a local /acceptance_test again; for a Friend's change, send them to the Friend as a Message and post them on its Subtask, where the user's Choices and Replies reach you through the Friend's relay (/atui, Friends, Relay). Once the changes are pushed (for a Friend's change, once the Friend reports them pushed), say so on the merge Decision's Thread and tell the user; they choose again on the same Decision. When `github` resolves the Decision, the pull request was merged or closed on GitHub: after a merge stop the app and go on as after step 5; after a close tell the user and wait.
5. On approval: /squash_and_merge_pr, then stop the app. A Friend's app stops when the Friend is retired, which setting its Subtask to `done` after the dev test does (/cleanup by the Orchestrator).
